Does a prompt pre-hook make Claude Code better?

Same codebase, same 24 developer questions, same model (Opus 5), same read-only tools. The only difference between arms: what gets injected before the prompt. 216 answers, scored two independent ways, every raw file kept.

The verdict in three sentences

On right-or-wrong, Opus 5 doesn't need the hook. With or without it, the model got 96–99% of the questions right on this small repo; the whole mechanical gap is one trap where the enhancer's answers were too long for a "shortly, why…" request.

On how good the answer is, the hook helps on the prompts that test behaviour — a blind second model preferred the enhancer's answer 70% of the time on vague, multi-part, review, QA and design prompts (it quantified before proposing, covered every part, flagged what it hadn't verified) — and was indifferent on plain fact-finding questions (53%).

But a static rules file gets you the same quality. Enhancer vs. rules-only: 50/50. The intent detection and the knowledge-base retrieval — the clever parts — did not measurably beat "write your working rules down once" for this model on this repo.

What the judge said — in its own words

Where the enhancer won (confidence 4/5):

g08 · envelope crash after create — "Both correctly identify the missing envelope bug with exact file/line and fix, but B additionally flags the downstream findOne() lacking relations (same crash class the user would hit next) and gives a concrete curl-based verification step."
s04 · make the feed faster — "B quantifies the N queries and missing indexes explicitly with file:line citations and states its interpretation of 'faster' before proposing fixes… A proposes similar fixes but with less rigorous before/after quantification."
g02 · someone edited my article — "B is more precise and honest about uncertainty (flags that the author relation isn't eager-loaded so a naive fix would silently pass, and explicitly notes unverified claims), while A asserts unverified specifics as fact."

Where it lost (confidence 4/5) — the pattern is consistent:

g03 · expired token gives 500 — "A pads with unsupported speculation (60-day-token theory, algorithms hardening) and excessive ancillary sections that reduce directness without adding correctness."
g09 · hearts always empty — "A pads with excessive detail (unverified claims like N+1 concerns, password-leak tangent, elaborate curl scripts) that reduce directness without adding correctness or completeness."
s01 · fix the 500 on favorite — "A applies the minimal direct fix as the ground truth specifies, while B introduces an unrequested helper-method refactor and pads the answer with extensive speculative analysis (blast radius, timestamps, an inline self-correction)."

Read together: the hook's quality bar ("state the blast radius", "name the test cases", "quantify first") makes the model thorough. On prompts that reward thoroughness — vague, multi-part, review, design — it wins. On a simple fact question or a one-line fix, the same bar reads as padding, and it loses.

## Cost before

Three SQL round trips per request, from `src/article/article.service.ts:66-94`:

1. `:67` — `SELECT * FROM follows WHERE followerId = ?`. `follows.followerId` is a plain `@Column()` with no `@Index` and no FK (`follows.entity.ts:9-13`), so InnoDB creates nothing implicitly → **full scan of the whole `follows` table**, which is global, not per-user. 10k users × 50 follows = 500k rows scanned to find ~50.
2. `:81` — `COUNT(DISTINCT article.id) WHERE authorId IN (…)`. The follow set is round-tripped back into SQL as a literal `IN` list.
3. `:91` — same `WHERE`, `ORDER BY article.created DESC`, and **no `LIMIT` unless the client sent `?limit=`** (`:83-88`). The RealWorld spec defaults `limit` to 20; this defaults to unbounded.

That last one dominates. 200 followed authors × 50 articles = 10,000 rows …

Where it hurt — "fix the 500 on favorite" (repeat 1, judge: no hook, both orders)

no hook2,775 chars · 25 turns
## Root cause

`POST /articles/:slug/favorite` → `ArticleService.favorite()` at `src/article/article.service.ts:131`:

```ts
const user = await this.userRepository.findOne(id);          // :133
const isNewFavorite = user.favorites.findIndex(...) < 0;     // :135  ← TypeError
```

`UserEntity.favorites` is a plain `@ManyToMany` with no `eager: true` (`src/user/user.entity.ts:33`), so `findOne(id)` returns `favorites === undefined`. `.findIndex` on it throws, nothing catches it, Nest returns 500.

## The patch

Two lines — `favorite()` at :133 and `unFavorite()` at :149 are identical and both crash:

```diff
-    const user = await this.userRepository.findOne(id);
+    const user = await this.userRepository.findOne(id, { relations: ['favorites'] });
```
full enhancer6,949 chars · 21 turns
## Root cause

`src/article/article.service.ts:135`

```ts
const isNewFavorite = user.favorites.findIndex(_article => _article.id === article.id) < 0;
```

`user` comes from `:133` — `findOne(id)` with no `relations` option. `favorites` is declared at `user.entity.ts:33-35` as a plain `@ManyToMany` + `@JoinTable()` with **no `eager: true`**, so TypeORM leaves the property `undefined` rather than `[]`.

The single source is the **load at :133**, not the read at :135 — and the same load is duplicated at `:149` for `unFavorite`, which is why the fix belongs in one loader, not two call sites. The file already demonstrates the correct form one method away, at `:181`…

**Why it surfaces now:** it doesn't — this is not a regression. `favorites` is never loaded on any code path, so *every* call to this endpoint has 500'd since the relation was added …

The hook adds ~3.4k input tokens per turn (mostly served from cache after the first call) and makes answers about 70% longer, for ~12% more per answer. Turn count is unchanged — it doesn't make the model explore more, it makes it write more. "Follows the format" = restatement line present and at least one file:line citation; reported, not scored.

Total spend: 216 Opus 5 answers $135.75 · 288 Sonnet 5 verdicts ≈ $25 · hook itself: ~150 ms per prompt, local, no network.

Corrections made along the way

The first interim numbers looked much better for the hook (86% → 98%). They were wrong, and the raw files are what caught it. Everything below is fixed in the repo; rescore.js re-grades saved answers without re-spending on the model.

  • 7 regex false negatives. Correct answers marked failed because they said "favorite() at line 133" instead of the file name, "wait for your call" instead of "confirm", "has id, body and a ManyToOne to Article" instead of "no author", "a success response does not prove a user was deleted" tripping a fabricated-execution check. Every failure was audited against the answer text before the final numbers.
  • Runner captured only the last message. When the model wrote its design, then called the ask-user tool (auto-dismissed headless), only the follow-up survived. Switched to stream-json and re-ran the 6 affected answers.
  • 99 "failures" were the Max plan's 5-hour session cap — recorded as failed runs, never scored, re-run the next day. A deny-list typo (MultiEdit) cost 2 more.
  • 8 judge verdicts lost to a greedy JSON regex — refilled; 288/288 in the final table.

Limitations — read before quoting a number

  • One small fixture, one model, one CLI version, three repeats. A snapshot, not a law. The 95% intervals are wide — treat 62% as "probably better", not "62%".
  • The traps were written by the hook's authors from real upstream bugs, but we chose which ones. Add your own: traps/*.json.
  • Opus 5 reads a 35-file repo in full on its own, so the retrieval layer had nothing to add here. On a large codebase — or with a cheaper model that doesn't explore as thoroughly — the answer may differ. That is the next experiment, not a claim.
  • Every run is a fresh session with a self-contained prompt. Real prompts are mostly mid-conversation follow-ups, which this cannot replay.
  • The judge is itself a model, with a measurable position bias (27 of 72 pairs flipped when the order flipped; the two orders are averaged so it cancels in the total but widens the noise).
